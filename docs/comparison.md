# What this is instead of

FerroSift does two things — transformation recipes and binary patterns — and
for each of them something else does part of the job better. This page says
which, and why, with the numbers coming from the same fixtures the rest of the
repository is checked against.

The figures below are regenerated by `cargo xtask ledger generate` and a stale
one fails CI. The prose is not generated, because "which of these should I use"
is a judgement rather than a measurement.

## Pick something else when

**You want the whole of CyberChef.** FerroSift has about half of the reference
catalog, and rx-chef has considerably more than FerroSift does.
[not-implemented.md](compatibility/not-implemented.md) lists every operation
that is missing and what each is waiting on. If the one you need is on that
list, nothing here helps you today.

**You want a graphical tool.** CyberChef is a web application with a drag-and-
drop recipe builder, a magic wand, and an input pane. FerroSift is a library
and a one-shot command. rx-chef additionally ships a TUI, a JSONL/JSON-RPC
server for editor integration, and an experimental C ABI.

**You need one transformation, fast.** If your program base64-decodes and
nothing else, use the `base64` crate. FerroSift is measurably slower than every
best-in-class specialist crate it has been compared against, at every size
measured — see [benchmarks.md](benchmarks.md). Paying a registry lookup, an
argument resolution and a budget check to call one codec buys you nothing when
the recipe never changes.

**You are already running Node.** CyberChef's own `cyberchefjs` package is the
reference implementation, which makes it byte-correct by definition. A port can
only approach that, and this one publishes exactly how close it has got.

**You want to read binary formats and nothing else.** ImHex is a full graphical
binary-analysis environment with the widest Pattern Language support there is,
and it is where the `.hexpat` ecosystem lives. If your work is opening a
firmware image and looking at it, take ImHex.

**You want the widest Rust Pattern Language.** `hxy-imhex-lang` is a Rust
implementation of the same language with a considerably larger language surface
than this crate's. FerroSift's pattern engine reads **11 of the 308** real
patterns ImHex itself ships — the number is on
[pattern-language-subset.md](pattern-language-subset.md) with the ranked reason
— and if breadth of the language is what you need rather than a transformation
runtime beside it, that is the better tool today.

## What is left

Four things, and they are the reason this exists rather than a claim that it is
better.

**Both halves in one runtime.** A recipe that decodes and decompresses, and a
pattern that reads the result — same library, same budgets, same targets, no
process boundary and no second dependency tree. Everything above does one half
of that; nothing does both.

**A compatibility claim with evidence attached.** Every operation that answers
to a CyberChef name is replayed against a pinned checkout of the reference, at
every recipe prefix, and the ones that are not are counted and named. The
number that matters is not how many operations exist but how many are *known*
to match, and where the known differences are. See
[the ledger](compatibility/ledger.md) and
[divergences.json](compatibility/divergences.json).

**Somewhere without an operating system.** The catalog is `no_std` + `alloc`
and forbids `unsafe`, and CI builds it for `thumbv7em-none-eabihf` and
`riscv32imac-unknown-none-elf` as well as for `wasm32-unknown-unknown`. A
recipe engine that runs on a microcontroller is a different tool from one that
runs on a workstation, and this is the one that does.
See [portability.md](portability.md).

**A bounded executor.** Every run carries explicit ceilings — input, output,
expansion ratio, steps, branches, flow depth, invocations, transient
allocation, work units — and structure, capabilities, arguments and the type
flow along the recipe as written are all settled before the first invocation
rather than part-way through it. That matters when the input is hostile and the
recipe came from somewhere else. What preflight cannot settle is where a jump
sends the counter; [docs/executor.md](executor.md) says exactly where the line
is, and [the safety matrix](safety-matrix.md) says what each operation can do.

252 of FerroSift's 254 answer to a CyberChef 11.4.0 name — **50.0% of the current reference catalog**. The other two are its own and have no reference name to claim. [not-implemented.md](compatibility/not-implemented.md) groups everything missing by what actually blocks it.
<!-- comparison:scale:end -->

Two cautions about that table. Operation counts are not comparable across
projects in the way the column suggests: what one project ships as a single
operation with a mode argument, another ships as three. And the two lower rows
are each project's own count, read once at the revision named; this repository
measures FerroSift continuously and has replayed nothing else.

That asymmetry is the whole reason the sections below grade FerroSift alone on
evidence, portability and limits. Grading another project on axes nobody
measured for it would be inventing a result, and a comparison that only its
author's project can win is not a comparison.

## Speed, against the reference

<!-- comparison:reference:begin -->
Across 30 measurements in 6 groups, every one a floor: **at least 15.8× to 197.2× faster**.

A floor, not a headline. Each row reads both sides as unfavourably as the data allows — the reference at its fastest batch against FerroSift at the slow end of its interval — so the ratio of the medians is larger than the number printed and is not printed. The per-group tables are in [benchmarks.md](benchmarks.md#against-the-reference-itself).
<!-- comparison:reference:end -->

This is the weakest of the three speed comparisons and the one worth least.
Beating a JavaScript implementation with a Rust one is the least a port should
manage, and it says nothing about whether the Rust is good.

## Speed, against the other Rust port

<!-- comparison:peer:begin -->
Measured on linux, against rx-chef at `99e26de96e28`, unmodified.

| Group | Sizes measured | How it came out |
|---|---:|---|
| `base64-encode` | 5 | mixed — faster at 2 of 5 sizes, between 1.10× faster and 1.62× slower |
| `hex-encode` | 5 | faster at every size, by 3.47× to 45.6× |
| `rot13` | 5 | mixed — faster at 4 of 5 sizes, between 2.13× faster and 1.97× slower |

Read the direction, not the digit: both arms are timed one after the other in one process, and two runs of that binary have disagreed by a quarter. The per-size rows are in [benchmarks.md](benchmarks.md#against-the-other-rust-port).
<!-- comparison:peer:end -->

This is the comparison that asks whether a library of *this* shape — registry,
operation trait, typed arguments, compiled pipeline — carries its structure
cheaply, because both sides pay that cost. It is also the only one of the three
where the result is genuinely mixed rather than one-sided.

## Speed, against specialist crates

Every competitive comparison is a loss, at every size measured.

That claim is not repeated here from the data, because the rule that decides it
— compare against the *fastest* arm in the group, refuse a verdict when the
intervals overlap, refuse one when the run was noisy, and require the win to
hold across more than one size — lives in the benchmark harness. A second
implementation of it on this page is how two pages come to disagree about the
same numbers. The claims table and the per-size tables with confidence
intervals are in [benchmarks.md](benchmarks.md#claims).

The gaps have a shape worth knowing before you choose. Roughly half a
microsecond of fixed per-call cost decides everything below about four
kilobytes, which is why the 16-byte rows are the most lopsided. Above that the
algorithms are the measurement, and the ports are written for exactness against
the reference rather than for speed. Neither is stated as an excuse; both are
things to fix, and the harness exists to make the work visible.

## Which to pick

| If you want | Use |
|---|---|
| The full catalog, interactively | CyberChef |
| The largest Rust catalog, with a CLI, TUI and editor server | rx-chef |
| One transformation as fast as Rust does it | the specialist crate |
| A graphical binary-analysis environment | ImHex |
| The widest Rust Pattern Language | `hxy-imhex-lang` |
| A transform recipe and a binary pattern in one portable runtime, under explicit limits, with the compatibility claim measured | FerroSift |

Nothing on that table is a claim about code quality. It is a claim about what
each thing was built to do, and five of the six rows point somewhere else.

The last row is the only one nothing else fills. Everything above it does its
own half better; what none of them does is both halves in one `no_std` library
whose compatibility claim is replayed against a pinned reference on every push.
